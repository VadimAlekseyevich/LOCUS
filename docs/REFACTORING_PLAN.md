### Как применять опыт osu!

1. **Время и ввод.** Выделить преобразование «событие устройства → время игры» и калибровку так, чтобы один и тот же поток можно было проиграть в тестах. Разработчики osu! явно разделяют обязанности Player, PauseContainer и RulesetInputManager. Для LOCUS достаточно минимального контракта для одного игрового режима. [Gameplay clocks](https://github.com/ppy/osu/wiki/Gameplay-clocks)
2. **Правила и отображение.** В osu! правила и обработка результатов имеют отдельные точки расширения. В LOCUS уже есть подходящая пара TurnJudge/PlayPresentation. Сначала сделать эту границу проверяемой на полном сценарии. [Ruleset](https://github.com/ppy/osu/blob/master/osu.Game/Rulesets/Ruleset.cs) · [JudgementProcessor](https://github.com/ppy/osu/blob/master/osu.Game/Rulesets/Scoring/JudgementProcessor.cs)
3. **Редактор и визуальные тесты.** Изолированная сцена редактора с реальными контролами позволяет проверять поведение до подключения всей игры. Аналог для LOCUS — загружать production RML вместе с presenter и тестовой моделью, а канву проверять через тот же layout, который получает ввод. [Implementing a ruleset editor](https://github.com/ppy/osu/wiki/Implementing-a-ruleset-editor) · [пример визуальной тестовой сцены](https://github.com/ppy/osu/blob/master/osu.Game/Tests/Visual/OsuGameTestScene.cs)

Сохраняем C++17, raylib и RmlUi на этом этапе. Переход на другой движок, отдельная библиотека для каждого экрана или универсальный API плагинов потребовали бы отдельного обоснования. Практическая цель — чтобы изменение скина, сетки редактора или меню можно было проверить независимо от результата прохождения.

## Карточки работ

Приоритет P0 означает риск для результата игрока, данных или процесса проверки. P1 — работа, которая окупится на текущих экранах и объёмах. P2 — доводка после измерений или перед публичным релизом. Зависимость в карточке означает необходимый результат предыдущей задачи. Нумерация задаёт постоянные ссылки, а не требование выполнить всё одним коммитом.

Rename сохраняет ID, copy/new создают новый, перенос пакетом сохраняет прежний. Коллизия ID при импорте имеет явный результат. Сообщить, какие форматы изменены и что произойдёт с дорелизной историей.

**Прогресс T06 (23.11.2026).** Авторитетный ID сложности живёт в chart JSON (`difficultyId`, 128 бит hex), независимо от имени файла и названия. Новая/скопированная сложность получает новый ID, повторный импорт того же источника сохраняет уже опубликованный ID, чужой дубликат в том же паке отклоняется. Стандартный gameplayRevision учитывает исходное игровое содержимое и тайминг без названия/пути, попытки v2 привязаны к `setId + difficultyId`, хранят fingerprint, judgementVersion и practiceRate. Формат результатов изменён с v1 на v2: старая дорелизная история остаётся на диске, но не подхватывается автоматически. Тесты round-trip, rename, copy, collision, revision history. Библиотечный скан отклоняет дубликаты difficultyId в одном Song Set и повторные setId в разных папках до публикации индекса. ZIP-импорт отказывает пакетам без ID или с повторным ID, а также рекурсивно сверяет setId со всеми установленными манифестами на диске, включая вложенные папки. Новая регрессия проверяет конфликт ID вложенного пака до публикации. ## Как брать работу следующей модели

1. Выбрать **одну карточку** или один явно пронумерованный шаг внутри неё. Проверить актуальный main, точки входа и ближайшие существующие тесты. Для P0 сначала зафиксировать воспроизведение или трассу.
2. До изменения записать инвариант и наблюдаемую проверку. Для скорости сохранить замер на той же машине. Для UI сохранить размер окна, DPI, данные и состояние фокуса. Для файловой операции описать состояние диска и черновика после ошибки.
3. Вносить законченный вертикальный срез через обычную точку входа. До первого релиза форматы можно менять. Если схема изменилась, указать старую/новую версию, затронутые файлы, последствия для пользовательских данных и обновить примеры.
4. Влить в main после проверки. В tracking issue зафиксировать ID карточки, SHA, команды, пройденные сценарии и оставшиеся непроверенные пункты. Карточка закрывается после её приёмки. Тест с mock-часами, headless layout и проверка на физическом устройстве отвечают на разные вопросы.

**Команды базовой проверки для Windows**

~~~powershell
cmake -S . -B build/windows -G "Visual Studio 17 2022" -A x64 -DLOCUS_BUILD_TESTS=ON -DLOCUS_BUILD_BENCHMARKS=ON
cmake --build build/windows --config Release --parallel 2
ctest --test-dir build/windows -C Release --output-on-failure
& build/windows/Release/locus.exe --loop-check
& build/windows/Release/locus.exe --screen-check
& build/windows/Release/locus.exe --session-check
& build/windows/Release/locus_route_preview_bench.exe
~~~

Короткое задание для передачи: «Выполни T__ из docs/REFACTORING_PLAN.md на свежем main LOCUS. Начни с указанного пользовательского сценария, сохрани перечисленные инварианты. Закрой критерии приёмки, сообщи SHA, результаты проверок и изменения форматов».
