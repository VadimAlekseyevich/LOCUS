## 1. Decision in one paragraph

**At the time of the decision**, choose modern C++17 + raylib 6.0 for the first Windows renderer/window, basic local audio transport and exploratory keyboard capture, with **raygui 5.0** for ordinary editor controls and **native Windows Common Item Dialogs** for local open/save file pickers. Use **CMake 3.25+ / Visual Studio 2022 MSVC x64**, **nlohmann/json v3.12.0** for the strict v1 JSON chart adapter, and **CTest + small in-repository tests**. Keep music-time mapping, route, judgement, and edit data as pure C++ code, independent of the window, render frames, raylib audio, and UI framework. Start with one coherent backend, not a dual-raylib/SDL abstraction layer.

This choice prioritizes **minimum practical audio/input latency and repeatable timing, stability, and maintainability**. A small binary is not the reason for this selection and is **not** a release constraint. Keeping a small architectural *surface* is useful; an application or asset package weighing tens or hundreds of megabytes is acceptable if justified by measured quality.

## 4. Module placement and dependency rules

```text
              app / SessionCoordinator
                  |            |
          platform adapters    editor feature/controller
          /       |      \       |
     raylib     Win32     storage   ChartDraft
     window     dialogs     |          |
     audio      files       |          |
     input       |          |          |
       \         |          |          |
        \        +----------+----------+
                         |
                 pure C++17 core
          Chart - Beat/Time - Route - Judgement
                         |
                 focused headless tests

Game view: raylib drawing of route/marker/HUD
Editor view: raylib drawing of timeline/grid + raygui controls
Test-play: normal SessionCoordinator with validated Chart snapshot
```

**Strict rules:**

- `src/core/` includes **no raylib, raygui, Win32 GUI, input polling, or device audio calls**. The chart format may use the JSON library in a narrow adapter, not expose JSON types to Route/Judgement.
- `src/platform/` owns raylib audio/window/input calls, native file dialogs, and filesystem access. No second chart or route implementation.
- `src/app/` owns lifecycle (start/pause/seek/stop/retry/test-play) and obtains one coherent clock snapshot per logical update.
- `src/ui/` renders snapshots; it does not compute judgements or mutate the authoritative chart path.
- `src/editor/` (or a small equivalent app submodule) holds ChartDraft and edit commands; Play and Editor use the same Route sampler.
- A view may use raygui for ordinary controls; a timeline may draw directly with raylib. **Do not implement an entire generic widget framework** simply to build this editor.
- Avoid new dependency-injection frameworks, plugin systems, ECS, or two parallel backends. Introduce separate backend adapters **only if concrete problems demand it**.

Directory suggestions are logical boundaries, not a mandate for many libraries or empty folders. The existing `mvp/spikes/raylib_audio/` program remains independent from production targets.

## 5. Song clock, input timing and low-latency risk plan

### 5.1 One music-time domain

The chosen raylib audio API is a **transport**, not by itself proof of a sample-accurate music clock.

1. Maintain a **double-precision logical SongClock** with an explicit monotonic reference (e.g. `std::chrono::steady_clock`); anchor/reanchor it on start, pause, resume, and seek.
2. Read raylib stream position as **observational/diagnostic evidence** to detect disagreement or discontinuities; do not blindly add `GetFrameTime()` every frame to advance music time.
3. Define a consistent path from input-capture monotonic timestamps to song time. A key event's capture time determines its grade, not the later render/update timestamp.
4. The route sampler consumes the same SongClock chart beat regardless of input. Wrong/Miss must never redirect movement.
5. Keep chart offset (author timing) separate from **user judgement calibration**, and implement both only under their assigned tasks.

**Important caveat:** A monotonic clock anchored when `PlayMusicStream()` is called does not automatically correspond to the time the first audio sample becomes audible. Backend buffering and device latency must be measured or estimated and compensated explicitly. This is **an unresolved technical risk**, not solved merely by choosing raylib.

### 5.2 Input capture

- The first implementation can capture fresh key-down edges at the earliest practical raylib input polling point, with an immediate high-resolution monotonic timestamp.
- Do not infer that `GetKeyPressed()` carries a hardware event timestamp; it does not. Inaccuracies caused by scheduling or frame stalls must be measured in T-09 and Q-12.
- If empirical measurements show significant frame-quantization/input latency, change **only the input adapter**, potentially to a Win32 event/raw-input path, without changing the pure Judgement model.
- Never use an event's rendering frame as its authoritative capture time, and never choose a key based on visible sprite movement.

### 5.3 Audio update and device latency

- Call `UpdateMusicStream()` reliably in the app loop while streaming; verify behavior under stalls and when the application is out of focus.
- Log reported stream time vs monotonic SongClock and seek/pause transitions; a displayed difference is **not** a direct measured DAC delay.
- If raylib's audio path proves too buffered, jittery, or unable to synchronize across devices, first investigate a targeted platform audio adapter. SDL3 is a plausible replacement backend **only after** a focused same-hardware experiment.
- Do not claim that static linkage, executable size, high FPS, or the owner's basic successful run proves minimum audio latency.

### 5.4 Objective pass conditions deferred to implementation tasks

| Gate | Objective evidence |
| --- | --- |
| T-06/T-07 | Transport and monotonic/stream clock measurements on representative lengths; pause/seek continuity documented |
| T-09/T-17 | Input edge timestamp tests; same captured event stream gives same grades under different frame schedules |
| P-03/P-04 | Visual marker position sampled from music time; no long center-crossing Wrap interpolation |

An objective high-precision latency promise can be made **only after** these tests. Do not set an arbitrary hard millisecond requirement without baseline measurements.

## 6. Editor architecture and minimum Windows UI

Choose **raygui 5.0 for common widgets**: text box, button, dropdown, slider and simple panels. Draw the grid and beat ruler/turn lane/playhead with raylib, since these are domain-specific visuals and do not justify a custom general-purpose UI toolkit.

Use **Windows Common Item Dialog** for local file picking/saving. This avoids reimplementing a reliable OS file picker and requires no network service. For the native dialogs, maintain correct COM apartment setup, Unicode conversion, focus return, and resource cleanup; wrap behind a narrow Platform method so editor code does not import Windows headers.

Chart JSON uses nlohmann/json v3.12.0 behind a dedicated decoder/encoder boundary. **Strict v1 validation is LOCUS-owned**: reject unknown fields, duplicate object members, invalid integer forms, out-of-bounds cells, invalid time values, and unsorted turn events. Do not assume that a generic JSON container rejects duplicate keys automatically; select a parser event handler or SAX-based approach as needed to meet CHART_FORMAT.md.

For editor audio selection and chart-relative paths, follow CHART_FORMAT.md. The user explicitly chooses when an audio file is copied into a chart folder; never upload their music or silently overwrite files.

## 7. Trade-offs and rejected alternatives

| Approach | Reason not chosen **for the first MVP** |
| --- | --- |
| SDL3 for all presentation/audio | No measured raylib blocker was reported in the A-07 local test; starting a second full stack adds engineering cost without evidence it reduces latency for this app. SDL3 remains the conditional A-08 fallback. |
| Native Win32 window + custom renderer | More low-level window/input/graphics work for a tiny 2D grid without proven timing benefit. Native dialogs only are enough initially. |
| Dear ImGui everywhere | Powerful, but its graphics/input backend integration would add additional choices and complexity for a timeline that must be custom anyway. Revisit only if raygui proves inadequate for editor usability. |
| Fully custom GUI framework | More focus, text, selection and editing bugs to maintain; raygui + native dialogs is a smaller starting point. |
| Godot/full game engine | Not prohibited, but no demonstrated timing/product benefit over the already working raylib spike; it adds workflow and architectural decisions. |
| Multiple audio backends immediately | Duplicate systems are expensive; hide direct dependencies at clear call sites without building a generic plugin framework. |
